# Real Web Push for a Next.js Personal Day-Planner (2026)

Single-user day planner. Server pushes a notification ~5 minutes before each scheduled task.
Must degrade gracefully to in-page toasts.

**Verified against live docs on 2026-10-01.** Every claim below is cited. Anything I could not
confirm is explicitly marked ⚠️ **UNVERIFIED**.

---

## TL;DR — the decisions that matter

| Question | Answer |
|---|---|
| Does `web-push` read env vars? | **No.** It reads none. Env var names are *your* convention. |
| VAPID private key format | **Raw 32-byte base64url string. NOT PEM.** |
| `public/sw.js` at root work? | **Yes.** Default scope is `/`. No `Service-Worker-Allowed` needed. |
| Max payload | **4096 octets** encrypted → **≤3993 octets** plaintext. |
| Does `userVisibleOnly: false` work? | **Not on the open web.** Chrome/Edge reject the Promise. |
| Vercel Hobby cron at `*/5 * * * *`? | **Impossible.** Hobby = once per day, ±59 min. Deployment fails. |
| Vercel serverless timers? | **No.** Functions are request-scoped and hard-killed at `maxDuration`. |
| pg_cron every 5 min? | **Yes** — `*/5 * * * *` (and even `[N seconds]`). |
| Push with browser fully quit? | **Documented as NO.** ⚠️ One contradicting Feb-2026 security report — see §5.1. |

**Primary scheduling recommendation: Supabase `pg_cron` + `pg_net` → Vercel route handler.**
**Fallback: self-hosted long-lived Node process with `node-cron`.** Reasoning in §4.4.

## 1) VAPID keys

### 1.1 Generating the keypair

`npx web-push generate-vapid-keys --json` is **still current in 2026**. Verified against the
library's own README and source.

Sources:
- <https://github.com/web-push-libs/web-push#command-line>
- <https://raw.githubusercontent.com/web-push-libs/web-push/master/src/vapid-helper.js>

```bash
# Option A — one-shot, no install (recommended)
npx web-push generate-vapid-keys --json

# Option B — local install
npm install web-push
npx web-push generate-vapid-keys --json

# Option C — global (not recommended for reproducibility)
npm install -g web-push
web-push generate-vapid-keys --json
```

**Exact output format** (verified verbatim from README + source):

```json
{"publicKey":"BGtkbcjrO12YMoDuq2sCQeHlu47uPx3SHTgFKZFYiBW8Qr0D9vgyZSZPdw6_4ZFEI9Snk1VEAj2qTYI1I1YxBXE","privateKey":"I0_d0vnesxbBSUmlDdOKibGo6vEXRO-Vu88QlSlm5j0"}
```

Notes on the format:
- Both values are **URL-safe base64 with NO `=` padding** and no whitespace.
- `publicKey` decodes to **exactly 65 bytes** (uncompressed P-256 point: `0x04 || X || Y`).
- `privateKey` decodes to **exactly 32 bytes** (raw scalar, little-endian).

Generated by this code path in `vapid-helper.js`:

```js
const curve = crypto.createECDH('prime256v1');
curve.generateKeys();
return {
  publicKey:   curve.getPublicKey().toString('base64url'),
  privateKey:  curve.getPrivateKey().toString('base64url')
};
```

There is **no PEM output mode and no OpenSSL path** in the current library. If you generate keys
with OpenSSL (`openssl ecparam -name prime256v1 -genkey`), you must manually extract the 32-byte
scalar and base64url it. Don't. Use `web-push`.

### 1.2 Env var names — the important correction

> **⚠️ `web-push` does not read ANY environment variables.**
> I read the entire library source (`src/index.js`, `src/web-push-lib.js`,
> `src/vapid-helper.js`, `src/urlsafe-base64-helper.js`). There is no `process.env` reference
> anywhere. `setVapidDetails(subject, publicKey, privateKey)` takes positional arguments only.
>
> So `process.env.WEB_PUSH_PUBLIC_KEY` / `WEB_PUSH_PRIVATE_KEY` / `WEB_PUSH_SUBJECT` are a
> **community convention** (popularised by the Mozilla codelab and countless Next.js tutorials),
> **not a library contract**. Nothing breaks if you rename them. Pick names, wire them yourself.

Two conventions in the wild. Either is fine — just be consistent:

**Convention A (`WEB_PUSH_*`)** — what most tutorials use:
```bash
WEB_PUSH_PUBLIC_KEY=BGtkbcjrO12YMoDuq2sCQeHlu47uPx3SHTgFKZFYiBW8Qr0D9vgyZSZPdw6_4ZFEI9Snk1VEAj2qTYI1I1YxBXE
WEB_PUSH_PRIVATE_KEY=I0_d0vnesxbBSUmlDdOKibGo6vEXRO-Vu88QlSlm5j0
WEB_PUSH_SUBJECT=mailto:you@example.com
```

**Convention B (`VAPID_*`)** — literally what the README's own `setVapidDetails` example uses:
```bash
VAPID_PUBLIC_KEY=BGtkbcjrO...
VAPID_PRIVATE_KEY=I0_d0vn...
VAPID_SUBJECT=mailto:you@example.com
```

I'll use `WEB_PUSH_*` throughout this guide. `.env.local`:

```dotenv
# ---------- Server-only. NEVER prefix with NEXT_PUBLIC_. ----------
WEB_PUSH_PUBLIC_KEY=BGtkbcjrO12YMoDuq2sCQeHlu47uPx3SHTgFKZFYiBW8Qr0D9vgyZSZPdw6_4ZFEI9Snk1VEAj2qTYI1I1YxBXE
WEB_PUSH_PRIVATE_KEY=I0_d0vnesxbBSUmlDdOKibGo6vEXRO-Vu88QlSlm5j0
WEB_PUSH_SUBJECT=mailto:you@example.com

# Shared secret for the scheduler endpoint (see §4)
CRON_SECRET=<at least 16 random chars>
```

### 1.3 `WEB_PUSH_SUBJECT` rules (these bite people)

Verified from `vapid-helper.js` → `validateSubject()`:

```js
export function validateSubject(subject) {
  if (!subject) throw new Error('No subject set in vapidDetails.subject.');
  const r = new URL(subject);
  if (!['https:', 'mailto:'].includes(r.protocol)) {
    throw new Error('Vapid subject is not an https: or mailto: URL. ' + subject);
  }
  if (r.hostname === 'localhost') {
    console.warn('Vapid subject points to a localhost web URI, which is unsupported by '
    + 'Apple\'s push notification server and will result in a BadJwtToken error when '
    + 'sending notifications.');
  }
}
```

Rules:
1. Must be `https:` or `mailto:`. Anything else **throws at runtime**.
2. Use a **real, externally reachable** contact address. `mailto:user@localhost` →
   **Apple Push returns `403 BadJwtToken`**. The README now calls this out explicitly.
3. Recommended: `mailto:you@yourdomain.com`.

### 1.4 Base64url public key → `Uint8Array` in the browser

`applicationServerKey` is typed `BufferSource` (`ArrayBufferView` / `ArrayBuffer`) in the IDL.
Passing the raw base64 string **works in Chrome but is not portable** and is deprecated. Convert.

The canonical implementation (identical to the one in the `web-push` README and MDN's
`js13kGames` PWA tutorial):

```ts
// lib/push/base64.ts  — safe in both Window and ServiceWorkerGlobalScope.
// Note: use bare `atob`, NOT `window.atob` — `window` does not exist in a service worker.
export function urlBase64ToUint8Array(base64String: string): Uint8Array {
  const padding = '='.repeat((4 - (base64String.length % 4)) % 4);
  const base64 = (base64String + padding).replace(/-/g, '+').replace(/_/g, '/');
  const rawData = atob(base64);
  const outputArray = new Uint8Array(rawData.length);
  for (let i = 0; i < rawData.length; ++i) {
    outputArray[i] = rawData.charCodeAt(i);
  }
  return outputArray;
}
```

**Confirmed decoder:** `atob()` (i.e. **standard base64**, not base64url) — the function's first job
is to translate base64url → standard base64 by replacing `-`→`+` and `_`→`/`, then re-padding with
`=` to a multiple of 4. `atob` is available on `WindowOrWorkerGlobalScope`, so this same helper
works inside `sw.js`.

Because the VAPID public key is **65 bytes** (multiple-of-4-unfriendly: 65 % 4 == 1), the padding
line matters. Don't strip it.

⚠️ **UNVERIFIED:** the newer `Uint8Array.fromBase64()` static. It removes the need for `atob`, but
I could not confirm cross-browser Baseline status as of 2026. Use `atob` for now.

## 2) Client subscription

### 2.1 Full client module

```ts
// lib/push/client.ts
// 'use client' — call from a Client Component only.

import { urlBase64ToUint8Array } from './base64';

export type PushState =
  | 'unsupported'   // browser/OS can't do push at all
  | 'default'       // supported, not asked yet
  | 'granted'
  | 'denied'
  | 'subscribed'
  | 'error';

export interface PushSupport {
  state: PushState;
  reason?: string;
  subscription?: PushSubscriptionJSON;
}

/**
 * Feature detection.
 *
 * Why these three checks:
 *  - 'serviceWorker' in navigator ............ no HTTPS / no SW support
 *  - 'PushManager' in window .................. no Push API (incl. iOS Safari in a normal tab)
 *  - 'showNotification' in ServiceWorkerRegistration.prototype
 *       WebKit's caniuse recommendation; catches Safari desktop < 16 and some embedded webviews
 *       where PushManager exists but notifications cannot be displayed.
 *       (See the note in this thread re: Safari's experimental feature flags.)
 */
export function pushSupported(): boolean {
  return (
    'serviceWorker' in navigator &&
    'PushManager' in window &&
    'showNotification' in ServiceWorkerRegistration.prototype
  );
}

export function currentPermission(): NotificationPermission | 'unsupported' {
  if (!pushSupported()) return 'unsupported';
  return Notification.permission;
}

async function getRegistration(): Promise<ServiceWorkerRegistration> {
  // Site-root relative URL so the same code works from any route.
  // public/sw.js sits at the origin root => default scope is '/'.
  return navigator.serviceWorker.register('/sw.js', { scope: '/' });
}

/** Register SW + read the existing subscription (no permission prompt). */
export async function getCurrentPushSubscription(): Promise<PushSubscription | null> {
  if (!pushSupported()) return null;
  try {
    const reg = await getRegistration();
    return await reg.pushManager.getSubscription();
  } catch {
    return null;
  }
}

/**
 * Ask for permission and subscribe. **Call this synchronously inside a user click handler.**
 */
export async function enablePush(vapidPublicKey: string): Promise<PushSupport> {
  if (!pushSupported()) {
    return { state: 'unsupported', reason: 'Push API not available in this browser/context.' };
  }

  // 1) permission. MUST be in the user-gesture call stack — see §2.2.
  let permission: NotificationPermission;
  try {
    permission = await Notification.requestPermission();
  } catch (e) {
    return { state: 'error', reason: `requestPermission threw: ${String(e)}` };
  }

  if (permission === 'denied') {
    // Only fixable in browser settings. Do NOT re-prompt on every load.
    return {
      state: 'denied',
      reason: 'Blocked in browser settings. Re-enable via the padlock/site-settings icon.',
    };
  }
  if (permission !== 'granted') {
    return { state: 'default', reason: 'User dismissed the prompt.' };
  }

  try {
    const reg = await getRegistration();
    // Reuse an existing subscription (avoids burning FCM quota / duplicate endpoints).
    const existing = await reg.pushManager.getSubscription();
    if (existing) {
      return { state: 'subscribed', subscription: existing.toJSON() };
    }

    const sub = await reg.pushManager.subscribe({
      // REQUIRED. See §2.3.
      userVisibleOnly: true,
      // 65-byte uncompressed P-256 point.
      applicationServerKey: urlBase64ToUint8Array(vapidPublicKey),
    });

    // POST to your server here (fire-and-forget is fine, but log failures).
    await fetch('/api/push/subscribe', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(sub.toJSON()),
    }).catch(() => undefined);

    return { state: 'subscribed', subscription: sub.toJSON() };
  } catch (e) {
    return { state: 'error', reason: String(e) };
  }
}

/** Unsubscribe + delete server-side record. Call from a user gesture. */
export async function disablePush(): Promise<void> {
  const sub = await getCurrentPushSubscription();
  if (!sub) return;
  await sub.unsubscribe();
  await fetch('/api/push/subscribe', { method: 'DELETE' }).catch(() => undefined);
}
```

### 2.2 User gesture: `requestPermission()` vs `subscribe()` — correcting the premise

Your premise ("`subscribe()` does not require a user gesture, `requestPermission()` does") is
**half right, and the half that's right is the wrong half to rely on.**

What the docs actually say:

- MDN, `PushManager.subscribe()` → "Responding to user gestures":
  > "`subscribe()` calls should be done in response to a user gesture, such as clicking a button…
  >  This is not only best practice — you should not be spamming users with notifications they
  >  didn't agree to — but **going forward browsers will explicitly disallow notifications not
  >  triggered in response to a user gesture. Firefox is already doing this from version 72**."
- MDN, `Notification.requestPermission()` requires transient activation ("sticky" permission only
  applies to `Notification` on some engines, and Chrome additionally requires a user gesture for
  the permission prompt to appear at all).
- WebKit's iOS announcement: "can request permission to receive push notifications **as long as
  that request is in response to direct user interaction** — such as tapping on a 'subscribe'
  button."

**Practical rule: put `Notification.requestPermission()` *and* `reg.pushManager.subscribe()` in the
same synchronous click handler** (as `enablePush()` above does). This satisfies every engine, today
and under the stated future direction. Never auto-subscribe on page load.

Source: <https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe#responding_to_user_gestures>

### 2.3 `userVisibleOnly: true` — what breaks if it's `false`

MDN, `subscribe()` → `userVisibleOnly`:

> "A boolean indicating that the returned push subscription will only be used for messages whose
> effect is made visible to the user.
> **Note:** This parameter is required in some browsers like Chrome and Edge. **They will reject
> the Promise if `userVisibleOnly` is not set to `true`.**"

So on the **open web**, `userVisibleOnly: false` ⇒ `subscribe()` **throws/rejects**. The escape
hatch (`userVisibleOnly: false`, silent pushes) shipped in **Chrome 121 but only for Manifest V3
extensions**, per Chrome's own extensions doc — not for your website.

Source: <https://developer.chrome.com/docs/extensions/how-to/integrate-web-push>

Related hard requirements on the SW side, all from MDN
(<https://developer.mozilla.org/en-US/docs/Web/API/Notification/Notification#exceptions>):

- `new Notification(...)` **throws `TypeError` inside a `ServiceWorkerGlobalScope`**. You must use
  `self.registration.showNotification(...)`. (Same page: the constructor also throws in "nearly all
  mobile browsers".)
- Apple is stricter still: *"Safari doesn't support invisible push notifications. Present push
  notifications to the user immediately after your service worker receives them. If you don't,
  Safari revokes the push notification permission for your site."*
  (<https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers>)

**Consequence for your design:** every `push` event handler must call `showNotification()` on every
code path, including your error path. Never `return` early with a silent `catch`.

### 2.4 Service worker: `public/sw.js`, path handling, headers

**A plain `public/sw.js` at the origin root works out of the box.** MDN: *"The default `scope` for
a service worker registration is the directory where the service worker script is located (resolving
`./` against `scriptURL`)."* Since `/sw.js` sits in `/`, default scope is `/` — already the widest
scope possible. **No `Service-Worker-Allowed` header is required.**

`Service-Worker-Allowed` is only needed when the script lives *below* the scope you want (e.g.
`/push/sw.js` claiming `{ scope: '/' }`).

Source: <https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register#scope>

What you *should* configure:

1. **`Cache-Control: no-cache` on `/sw.js`** — otherwise a stale cached worker is never replaced
   and your handler edits silently don't ship. Next.js serves `public/` verbatim, so set this in
   `next.config`:

```ts
// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  async headers() {
    return [
      {
        // Service worker: never cache, or updates never land.
        source: '/sw.js',
        headers: [
          { key: 'Cache-Control', value: 'public, max-age=0, must-revalidate' },
          { key: 'Service-Worker-Allowed', value: '/' }, // harmless, documents intent
        ],
      },
      {
        // Icons referenced from the SW / notifications. Same-origin, immutable.
        source: '/icons/:path*',
        headers: [{ key: 'Cache-Control', value: 'public, max-age=31536000, immutable' }],
      },
    ];
  },
};
export default nextConfig;
```

2. **`worker-src` in your CSP** if you have one (MDN flags this as the XSS-mitigation for the
   `scriptURL` injection sink).

3. Don't use `swSrc`/`@serwist/nextjs` unless you want a build pipeline. For a single planner,
   a hand-written `public/sw.js` is simpler and has no bundler surprises — but remember it **cannot
   import from `app/` or `lib/`**; everything must be inline.

### 2.5 The `push` handler — modern, handles both `json()` and `text()`

Two traps:
1. **`event.data` can be `null`** when the server sent a payload-less push
   (`webpush.sendNotification(sub)` with no payload — legal per the `web-push` README). Always
   guard.
2. `PushMessageData` methods are **re-callable** (unlike `fetch()` bodies), so calling `.text()`
   then `.json()` is legal — but parsing one `text()` is simpler and always correct.

`public/sw.js`:

```js
/* eslint-disable no-restricted-globals */

const FALLBACK = { title: 'Study Table', body: 'You have an upcoming task.', url: '/' };

/**
 * Read a push payload regardless of whether the server sent JSON or plain text.
 * Returns null for a payload-less push.
 */
async function readPushData(event) {
  if (!event.data) return null;             // payload-less push
  const text = await event.data.text();    // .text() works for both JSON and plain text
  if (!text) return null;
  try {
    return JSON.parse(text);
  } catch {
    return { body: text };
  }
}

self.addEventListener('push', (event) => {
  // `waitUntil` is REQUIRED — without it the SW can be terminated mid-handler.
  event.waitUntil(
    (async () => {
      const data = (await readPushData(event)) ?? FALLBACK;

      const title = data.title ?? FALLBACK.title;
      const options = {
        body: data.body ?? FALLBACK.body,
        // `url` is a URL string; `taskId` travels along for the click handler.
        data: { url: data.url ?? '/', taskId: data.taskId ?? null },
        icon: '/icons/icon-192.png',
        badge: '/icons/badge-72.png',
        // Dedupes/replaces. Also required if you set renotify.
        tag: data.tag ?? `task-${data.taskId ?? 'generic'}`,
        // Desktop Chrome/Edge: stays on screen until dismissed.
        requireInteraction: true,
        timestamp: data.at ?? Date.now(),
        // Desktop has no vibration motor -> ignored. Harmless.
        vibrate: [200, 100, 200],
        // Desktop Chrome/Edge DO render these. Skip `type: 'text'` (reply) — desktop doesn't
        // support inline text input and it throws on some engines.
        actions: [
          { action: 'start', title: 'Start' },
          { action: 'snooze', title: 'Snooze 5 min' },
        ],
      };

      // MUST NOT skip this on any path — Safari revokes permission otherwise (§2.3).
      await self.registration.showNotification(title, options);

      // Optional: wake any open tab so it can render an in-page toast instead of / in addition to
      // the OS notification.
      const clients = await self.clients.matchAll({ type: 'window', includeUncontrolled: true });
      for (const client of clients) {
        client.postMessage({ type: 'PUSH', payload: data });
      }
    })()
  );
});

/**
 * Subscribe is a transient-user-activation-gated call in practice (see §2.2).
 * Handle 404/410 on the server and delete the record instead (see §3.3).
 */
self.addEventListener('pushsubscriptionchange', (event) => {
  // ⚠️ Chrome does NOT implement this event (crbug.com/646721). Safari does not either.
  // Your server-side 404/410 pruning (§3.3) is the real safety net.
  event.waitUntil(
    (async () => {
      try {
        const sub = await self.registration.pushManager.getSubscription();
        if (sub) {
          await fetch('/api/push/subscribe', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify(sub.toJSON()),
          });
        }
      } catch {}
    })()
  );
});
```

Wait — modern `PushEvent` note: `PushEvent` extends `ExtendableEvent`, so `event.waitUntil()` is
always available. `ExtendableMessageEvent` is the *other* type (used by `self.postMessage` /
`MessageChannel` in a SW), **not** by `push`. If you use `client.postMessage(...)` from the page
side, the receiving listener in the SW would be `ExtendableMessageEvent`. You don't need it for push.

Sources:
- <https://developer.mozilla.org/en-US/docs/Web/API/PushMessageData>
- <https://developer.mozilla.org/en-US/docs/Web/API/PushEvent>
- <https://developer.mozilla.org/en-US/docs/Web/API/Push_API>

### 2.6 `notificationclick`: focus an existing tab, else open a window

```js
self.addEventListener('notificationclick', (event) => {
  // Always close, on every branch (Android doesn't auto-close: crbug.com/463146).
  event.notification.close();

  const data = (event.notification.data && typeof event.notification.data === 'object')
    ? event.notification.data
    : {};
  const target = typeof data.url === 'string' && data.url.startsWith('/') ? data.url : '/';

  // Action buttons -> handle distinctly.
  if (event.action === 'snooze') {
    event.waitUntil(
      fetch('/api/push/snooze', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ taskId: data.taskId }),
      }).catch(() => undefined)
    );
    return;
  }

  // waitUntil keeps the SW alive so the focus/navigate actually completes.
  event.waitUntil(
    (async () => {
      // includeUncontrolled: true catches the very first visit, where no client is controlled yet.
      const clientList = await self.clients.matchAll({
        type: 'window',
        includeUncontrolled: true,
      });

      for (const client of clientList) {
        // Same-origin only. Compare origins, not url prefixes (defence against openWindow abuse).
        if (new URL(client.url).origin !== self.location.origin) continue;

        // Chrome/Edge support focus()+navigate(); Safari supports focus() only.
        await client.focus();
        if ('navigate' in client) {
          try {
            await client.navigate(new URL(target, self.location.origin).href);
          } catch {
            // navigate() rejects if the client is not currently controlled (e.g. hard reload).
            // Focus alone is an acceptable fallback.
          }
        }
        return;
      }

      if (self.clients.openWindow) {
        await self.clients.openWindow(new URL(target, self.location.origin).href);
      }
    })().catch((err) => console.error('[sw] notificationclick failed', err))
  );
});
```

Notes:
- `client.navigate()` is Chrome/Edge-only. Guarded above.
- Restricting to same-origin also blocks the "any pushed site can tabnab" issue: your own service
  worker can only open windows on your own origin anyway, but be explicit.
- Source: <https://web.dev/articles/push-notifications-notification-behaviour#notification_click_event>

### 2.7 Notification options that actually work on desktop Chrome/Edge

| Option | Chrome/Edge desktop | Firefox desktop | macOS Safari | Notes |
|---|---|---|---|---|

## 3) Server side

### 3.1 `setVapidDetails` + `sendNotification`

```ts
// lib/push/server.ts   — server-only. Add `import 'server-only';` at the top.
import 'server-only';
import webpush from 'web-push';

// --- Configure ONCE at module load. -------------------------------------------
const SUBJECT   = process.env.WEB_PUSH_SUBJECT;
const PUBLIC    = process.env.WEB_PUSH_PUBLIC_KEY;
const PRIVATE   = process.env.WEB_PUSH_PRIVATE_KEY;

if (!SUBJECT || !PUBLIC || !PRIVATE) {
  throw new Error(
    'Missing WEB_PUSH_SUBJECT / WEB_PUSH_PUBLIC_KEY / WEB_PUSH_PRIVATE_KEY. ' +
    'Generate with: npx web-push generate-vapid-keys --json'
  );
}

// Throws loudly at boot if the keys are the wrong shape (wrong length, PEM, `=` padding...).
// This is the single best guard against a bad rotation.
webpush.setVapidDetails(SUBJECT, PUBLIC, PRIVATE);

export interface StoredSubscription {
  endpoint: string;
  expirationTime: number | null;
  keys: { p256dh: string; auth: string };
}

/**
 * RFC 8291 caps the *plaintext* at 3993 octets. Throwing beats silently getting a
 * 413 from FCM. Set the limit slightly conservative.
 */
const MAX_PLAINTEXT_BYTES = 3900;

export function sendReminder(
  sub: StoredSubscription,
  payload: { title: string; body: string; url: string; taskId: string; at?: number; tag?: string }
) {
  const body = JSON.stringify(payload);
  const bytes = Buffer.byteLength(body, 'utf8');
  if (bytes > MAX_PLAINTEXT_BYTES) {
    throw new Error(`Push payload too large: ${bytes} bytes (max ${MAX_PLAINTEXT_BYTES}).`);
  }

  return webpush.sendNotification(sub, body, {
    TTL: 3600,        // seconds. 1h is plenty for a 5-min-early reminder.
    urgency: 'high',  // 'very-low' | 'low' | 'normal' | 'high'  -> 'high' tries to deliver now
    topic: `task-${payload.taskId}`.slice(0, 32), // coalesces; ALSO makes retries idempotent
    // contentEncoding defaults to 'aes128gcm' — leave it. Don't pass 'aesgcm'.
  });
}
```

`options` accepted by `sendNotification` (from the README + `web-push-lib.js`):
`gcmAPIKey`, `vapidDetails`, `timeout`, `TTL`, `headers`, `contentEncoding`, `urgency`, `topic`,
`proxy`, `agent`. Passing an **unknown** key throws `'X' is an invalid option.` — the library
validates strictly, which is helpful.

`TTL` default is **2419200 seconds (4 weeks)** per `DEFAULT_TTL` in source. Override it.

### 3.2 Payload limits — must it be encrypted? How big?

**Yes, encrypted — mandatory for any payload.** RFC 8291 (Message Encryption for Web Push), §4:

> "A push service is not required to support more than **4096 octets** of payload body (see
> Section 7.2 of RFC8030). Absent header (86 octets), padding (minimum 1 octet), and expansion for
> AEAD_AES_128_GCM (16 octets), this equates to, at most, **3993 octets of plaintext**."

**The numbers to remember:**
- **4096 octets** — hard ceiling on the encrypted request body (RFC 8030 §7.2 minimum guarantee).
- **3993 octets** — max plaintext after `aes128gcm` overhead.

Chrome's older blog quotes **4078 bytes** of usable payload (4096 − 16 tag − 2 padding), which
predates the 86-octet header accounting. Use **3900** as a working budget. Your payload
(`{"title":"...","body":"...","url":"/?task=1","taskId":"1","at":...}`) is ~100–200 bytes, so this
never bites in practice — but assert it anyway.

You may send a **payload-less** push (`webpush.sendNotification(sub)` with no second argument).
That produces `Content-Length: 0` and no `Content-Encoding` header — legal, but then the SW gets
`event.data === null`. Don't do it for reminders; you need the task title.

Content encoding: `web-push` supports `aes128gcm` (**default, use this**) and the legacy `aesgcm`.
The legacy path adds `Encryption: salt=...` and a `Crypto-Key: dh=...` header. Modern browsers
(Firefox 52+, Chrome 55+, Safari 16+) all do `aes128gcm`. Never pass `contentEncoding`.

Sources: <https://www.rfc-editor.org/rfc/rfc8291.html#section-4>, <https://datatracker.ietf.org/doc/html/rfc8030#section-7.2>

### 3.3 Detecting and pruning dead subscriptions (404/410)

`web-push` rejects with a `WebPushError` carrying `statusCode`, `headers`, `body`, `endpoint`
(`sendNotification` → `new WebPushError('Received unexpected response code', statusCode, ...)` for
any non-2xx).

**Error-code semantics (RFC 8030 §7.3 + push-service practice):**

| Status | Meaning | Correct action |
|---|---|---|
| **404** | Endpoint no longer exists (site data cleared, PWA uninstalled, profile wiped). | **Delete the subscription.** Permanent. |
| **410 Gone** | Subscription explicitly expired/unsubscribed. Mozilla Autopush body is literally `"push subscription has unsubscribed or expired"`. | **Delete the subscription.** Permanent. |
| 401 | No/invalid VAPID `Authorization` header. | Fix server config. Do NOT delete. |
| 403 Forbidden | Invalid VAPID signature/claims — e.g. `BadJwtToken` from an Apple push service because your VAPID `sub` is `localhost`/`mailto:user@localhost`. | Fix `WEB_PUSH_SUBJECT`. Do NOT delete. |
| 429 | Rate limited by the push service. | Back off. Do NOT delete. |
| 5xx | Push service failure. | Retry with backoff. Do NOT delete. |

```ts
// lib/push/dispatch.ts
import webpush from 'web-push';
import { sendReminder, type StoredSubscription } from './server';

export interface SendResult {
  ok: boolean;
  /** true => the subscription is permanently dead and must be deleted. */
  prune: boolean;
  status?: number;
  error?: string;
}

/** Statuses that mean "this endpoint is gone forever". */
const PERMANENT_GONE = new Set([404, 410]);

export async function sendReminderTo(
  sub: StoredSubscription,
  payload: Parameters<typeof sendReminder>[1]
): Promise<SendResult> {
  try {
    const res = await sendReminder(sub, payload);
    return { ok: true, prune: false, status: res.statusCode };
  } catch (err: unknown) {
    // web-push exports WebPushError, but duck-typing avoids a version-coupling import.
    const status = (err as { statusCode?: number })?.statusCode;
    const body   = (err as { body?: string })?.body ?? '';

    if (status !== undefined && PERMANENT_GONE.has(status)) {
      return { ok: false, prune: true, status, error: body };
    }

    // 401 / 403 / 429 / 5xx / network: transient or config. KEEP the subscription.
    return {
      ok: false,
      prune: false,
      status,
      error: `${body || String(err)}`,
    };
  }
}
```

Pruning loop (the whole point: **delete on 404/410, never on anything else**):

```ts
// lib/push/sweep.ts
import { sendReminderTo } from './dispatch';
import type { StoredSubscription } from './server';

export interface SendOutcome {
  taskId: string;
  ok: boolean;
  prune: boolean;
  status?: number;
  error?: string;
}

export async function dispatchReminders(
  due: { taskId: string; title: string; startsAt: Date; url: string }[],
  subscriptions: StoredSubscription[],
  onPrune: (endpoint: string) => Promise<void>,
  onSent: (taskId: string, endpoint: string) => Promise<void>,
): Promise<SendOutcome[]> {
  const outcomes: SendOutcome[] = [];

  // One push message per (task, subscription). For a single user this is a 1xN loop.
  for (const task of due) {
    for (const sub of subscriptions) {
      const result = await sendReminderTo(sub, {
        title: 'Starting in 5 minutes',
        body: `${task.title} — ${task.startsAt.toLocaleTimeString()}`,
        url: task.url,
        taskId: task.taskId,
        // Set on the server; the SW also accepts it via `timestamp`.
        at: task.startsAt.getTime(),
        tag: `task-${task.taskId}`,
      });

      if (result.prune) {
        await onPrune(sub.endpoint);          // <-- DELETE the row
      } else if (result.ok) {
        await onSent(task.taskId, sub.endpoint);
      }

      outcomes.push({ taskId: task.taskId, ...result });
    }
  }

  return outcomes;
}
```

Keep the `push_subscriptions` table tiny:

```sql
-- Postgres / Supabase
create table if not exists push_subscriptions (
  endpoint    text primary key,          -- the endpoint IS the identity
  p256dh      text not null,
  auth        text not null,
  expiration_time bigint,
  created_at  timestamptz not null default now(),
  last_ok_at  timestamptz,
  failure_count int not null default 0
);

-- Idempotency guard so a duplicate cron invocation doesn't double-notify.
create table if not exists notification_log (
  task_id     text not null,
  endpoint    text not null,
  sent_at     timestamptz not null default now(),
  primary key (task_id, endpoint)
);
```

`endpoint` is a **bearer capability URL** — MDN: *"The endpoint URL therefore needs to be kept
secret."* Treat the table as a secret store. Don't log it, don't ship it to the client beyond the
user's own browser, and add RLS.

## 4) Scheduling — 5-minutely, no browser tab open

This is the part that decides whether the whole thing works.

### Option A — Vercel Cron

**Config syntax** (verified: <https://vercel.com/docs/cron-jobs>):

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "crons": [
    {
      "path": "/api/cron/reminders",
      "schedule": "*/5 * * * *"
    }
  ]
}
```

- 5-field POSIX cron. **UTC only.**
- No `MON`/`JAN` names. Cannot combine day-of-month with day-of-week.
- Triggered as an **HTTP GET** to the production deployment URL.
- Requests carry `User-Agent: vercel-cron/1.0` and header `x-vercel-cron-schedule: */5 * * * *`.
- Only registered on **production** deployments, not previews.

**Hobby-plan limits as of 2026** (verified: <https://vercel.com/docs/cron-jobs/usage-and-pricing>,
<https://vercel.com/changelog/cron-jobs-now-support-100-per-project-on-every-plan>):

| Plan | Cron jobs / project | Min interval | Precision |
|---|---|---|---|
| **Hobby** | 100 | **Once per day** | **Per-hour (±59 min)** |
| Pro | 100 | Once per minute | Per-minute |
| Enterprise | 100 | Once per minute | Per-minute |

> "Hobby accounts are limited to cron jobs that run **once per day**. Cron expressions that would
> run more frequently **will fail during deployment**." … *"Expressions like `0 * * * *` (per-hour)
> or `*/30 * * * *` (every 30 minutes) will fail deployment with the error: Hobby accounts are
> limited to daily cron jobs."*

**⚠️ Verdict: Option A is DEAD for a 5-minute trigger on Hobby.** `*/5 * * * *` fails the deploy.
It requires **Vercel Pro ($20/mo)**. On Pro, accuracy is within the specified minute.

Two more Pro caveats: **no retries** on failure, and **duplicate invocations happen** — so the
handler must be idempotent (`notification_log` PK above handles this).

`CRON_SECRET` — Vercel automatically sends the value of the `CRON_SECRET` env var as
`Authorization: Bearer <value>`:

```ts

export async function GET(req: NextRequest) {
  const expected = process.env.CRON_SECRET;
  if (!expected || req.headers.get('authorization') !== `Bearer ${expected}`) {
    return new Response('Unauthorized', { status: 401 });
  }

  return Response.json({ ok: true });

```

### Option B — self-hosted long-lived Node (`node-cron` / `setInterval`)

**Verified claim: Vercel serverless functions CANNOT hold timers.** A Vercel Function exists only
for the duration of an HTTP request, and is hard-terminated at `maxDuration` (Hobby: **300 s
default = maximum**; Pro/Ent: 300 s default, 800 s max, 1800 s beta — source:
<https://vercel.com/docs/functions/limitations>). There is no "keep-alive" primitive that
survives the response. The official Vercel docs confirm the pattern: *"Periodic tasks: celery beat
requires a long-running process. Use Vercel Cron Jobs to call a route that enqueues Celery tasks."*
(<https://vercel.com/docs/frameworks/backend/celery>). Even `waitUntil` is bounded by
`maxDuration`. A `setInterval` inside a route handler will fire once or twice and then die with the
instance.

So Option B means **a real server** (Fly.io, Railway, Render, a VPS, your NAS/always-on desktop):

```bash
npm install node-cron web-push
```

```ts
// scheduler.ts  — run with: npx tsx scheduler.ts   (or compile and `node dist/scheduler.js`)
import cron from 'node-cron';
import { dispatchReminders } from './lib/push/sweep';
import { loadDueTasks, loadSubscriptions, deleteSubscription, recordSent } from './db';

async function tick() {
  const now = Date.now();
  const due = await loadDueTasks({
    // Fire the reminder when we cross T-5min. The 60s slack absorbs drift so a task created
    // 30s before its T-5 mark still gets notified.
    from: new Date(now - 60_000),
    to:   new Date(now + 5 * 60_000),
  });

  if (due.length === 0) return;

  const subs = await loadSubscriptions();
  await dispatchReminders(due, subs, deleteSubscription, recordSent);
  console.log(`[cron] processed ${due.length} task(s), ${subs.length} subscription(s)`);
}

// Every 5 minutes. `cron.schedule` fires at the wall-clock boundary (:00, :05, :10, ...),
// NOT 5 minutes after process start.
cron.schedule('*/5 * * * *', () => {
  tick().catch((e) => console.error('[cron] tick failed', e));
});

console.log('scheduler up; firing every 5 min');
```

If you'd rather not depend on `node-cron`, `setInterval` aligned to the next 5-minute mark:

```ts
const PERIOD = 5 * 60_000;

  const now = Date.now();
  const delay = PERIOD - (now % PERIOD);   // next :00/:05/:10 boundary
  setTimeout(() => {
    tick().catch(console.error).finally(arm);
  }, delay);
}
arm();
```

### Option C — Supabase `pg_cron` + `pg_net` ✅ RECOMMENDED

This is the primary recommendation for your specific situation.

**Verified pg_cron granularity** (<https://github.com/citusdata/pg_cron#cron-syntax>):

> "pg_cron also allows you: to use `$` to indicate last day of the month. **to use `[1-59] seconds`
> to schedule a job based on an interval.**"

Example schedules from the same README: `'10 seconds'`, `* * * * *`, **`*/5 * * * *`**, `0 * * * *`.
Supabase's own docs: *"can run anywhere from **every second to once a year**"*, and recommend *"no
more than 8 Jobs run concurrently"* / *"no more than 10 minutes"* each
(<https://supabase.com/docs/guides/cron>).

**✔ `*/5 * * * *` works. pg_cron is more than precise enough.**

`pg_net` is asynchronous by default, so the cron job enqueues and returns immediately — it never
blocks on your Vercel function
(<https://supabase.com/docs/guides/database/extensions/pg_net>).

**Step 1 — enable extensions**

**Step 2 — store the shared secret in `vault`**

**Step 3 — the schedule + HTTP call**

Notes on `pg_net`:
- Responses are stored 6 hours; queue is an **unlogged** table (lost on unclean DB crash).
- Rate ceiling ~200 req/sec — 288/day is nothing.
- ⚠️ **Limitation: "Can only make POST requests with JSON data."** No PATCH/PUT. Your cron handler
  **must** be a `POST` route handler, not a `GET`. (Vercel Cron sends `GET` — that's fine, the
  handler can accept both; see below.)

Therefore make the route handler accept **both** GET and POST:

```ts
// app/api/cron/reminders/route.ts
import { NextRequest } from 'next/server';
import { dispatchReminders } from '@/lib/push/sweep';

export const maxDuration = 60;
export const dynamic = 'force-dynamic';   // never cache this

// Single implementation, two method signatures.
async function handle(req: NextRequest) {
  // 1. Auth. Works for BOTH Vercel Cron (auto-injects Authorization from CRON_SECRET)
  //    and pg_net (sends Authorization from vault).
  const expected = process.env.CRON_SECRET;
  if (!expected || req.headers.get('authorization') !== `Bearer ${expected}`) {
    return new Response('Unauthorized', { status: 401 });
  }

  // 2. Cheap idempotency: short TTL so overlapping runs don't both send.
  //    Vercel sets this header for its own cron invocations.
  const fromVercel = req.headers.get('user-agent')?.startsWith('vercel-cron/') ?? false;
  const schedule   = req.headers.get('x-vercel-cron-schedule');
  console.log(`[cron] trigger=${fromVercel ? 'vercel-cron' : 'external'}${schedule ? ` (${schedule})` : ''}`);

  const now = Date.now();
  const due = await loadDueTasks({
    from: new Date(now - 90_000),          // 90s lookback = covers missed + duplicate runs
    to:   new Date(now + 5 * 60_000),
  });

  const subs = await loadSubscriptions();
  const outcomes = await dispatchReminders(due, subs, deleteSubscription, recordSent);

  return Response.json({
    ok: true,
    tasks: due.length,
    subs: subs.length,
    sent: outcomes.filter((o) => o.ok).length,
    pruned: outcomes.filter((o) => o.prune).length,
    failed: outcomes.filter((o) => !o.ok && !o.prune).length,
  });
}

export const GET  = handle;   // Vercel Cron sends GET
export const POST = handle;   // pg_net can only send POST
```

**Prerequisite:** the Vercel route must be publicly reachable, so `CRON_SECRET` must be set in the
**production** Vercel environment, and the deployment must be a production deploy (cron is not
registered on previews).

### 4.4 Recommendation

**PRIMARY: Option C — Supabase `pg_cron` (`*/5 * * * *`) + `pg_net` → Vercel `POST /api/cron/reminders`.**

Reasoning:
1. **Vercel Hobby physically cannot do it.** Once-per-day, ±59 min, and `*/5 * * * *` *fails the
   deployment*. You said Vercel is the likely host — so you need a trigger Vercel can't give you.
2. **Zero marginal cost.** Supabase's free Postgres tier is always-on and pg_cron/pg_net are
   included. The alternative, Vercel Pro, is $20/mo forever.
3. **Architecture stays clean.** The app remains a stateless serverless Next.js app. The scheduler
   is infrastructure that pokes an authenticated HTTP endpoint — swap Supabase for any external
   scheduler later without touching app code.
4. **Precision.** pg_cron gives per-minute (and per-second) granularity; you're asking for
   every-5-minutes.
5. **Observability.** `cron.job_run_details` and `net._http_response` give you a real execution
   history. Vercel Hobby cron has none, and Vercel sends no failure alerts.
6. The 90-second lookback window in `loadDueTasks` makes the whole thing **idempotent and
   self-healing** — a missed 5-minute slot is caught on the next run, and duplicate invocations
   are absorbed by the `notification_log` primary key. That directly answers Vercel's documented
   "will not retry" + "may occasionally invoke more than once" caveats.

**FALLBACK: Option B — self-hosted `node-cron` (`*/5 * * * *`) on a long-lived Node process.**

Reasoning:
- If you'd rather not add Supabase as a dependency, or if pg_cron ever becomes the wrong fit, a
  ~40-line `node-cron` loop on a $0–$5/mo always-on instance is the simplest thing that definitely
  works.
- **Not** a Vercel function — timers there cannot outlive the request (§Option B).
- If you go this route, keep the exact same `dispatchReminders()` handler and call it from the
  loop, so the payload/pruning/idempotency logic is shared with the pg_cron path.

**Do NOT use Option A on Hobby.** If you end up on Vercel Pro anyway, add
`{"path": "/api/cron/reminders", "schedule": "*/5 * * * *"}` to `vercel.json` as a *third*
belt-and-braces trigger — the auth check and idempotency make double-triggering harmless.

## 5) Failure modes

### 5.1 Browser fully quit on desktop

**Documented behaviour: push does NOT arrive if the browser process is not running.**

web.dev's canonical answer (<https://web.dev/articles/push-notifications-faq>):

> "**On desktop OS's**, it's more nuanced… In the context of receiving push messages on desktop,
> you will receive messages when the browser is **running**… This means the browser can have **no
> windows open**, and you'll still receive the push message in your service worker, because the
> browser is running in the background.
> **The only time a push won't be received is when the browser is completely closed**, i.e. not
> running at all (no marking). The same applies for Windows…"

On **Android** it's the opposite: "The Android OS is designed to listen for push messages and upon
receiving one, **wake up the appropriate Android app**… regardless of whether the app is closed or
not."

OneSignal's operator docs agree for the desktop case
(<https://documentation.onesignal.com/docs/en/notifications-not-shown-web-push.md>):
> "**Browser is closed** — Browsers won't show push notifications unless they are running. If you
> open the browser before the Time to live (TTL) expires on a sent notification, it will pop up."

That TTL behaviour is your one real mitigation — hence `TTL: 3600` in §3.1. If the browser comes
back within an hour, the message lands.

⚠️ **CONTRADICTORY EVIDENCE — treat with caution.** A February 2026 Chromium security report
(issue **485535962**, *"Web Push notification suppression bypass enables silent persistent browser
C2"*) claims the reporter observed push delivery **with Chrome completely closed on macOS**,
executed service-worker code, and produced zero visible notifications. This directly contradicts
web.dev and OneSignal.

- I could **not** verify this issue's contents directly (the Chromium issue tracker requires
  authentication, so I only have the indexed excerpt) and I could not find corroborating
  independent reporting or a Chromium response.
- **Do not architect around it.** The documented behaviour is the safe assumption.
- ⚠️ It is a *security* report about suppressing notifications (`showNotification()` immediately
  followed by `close()`), not about delivery-with-browser-closed. It is possible the reporter's
  Chrome process was still resident (macOS "Keep alive" for background apps, or a lingering
  `chrome_crashpad_handler`/background process). That would be consistent with web.dev.

**Chromium flags / profiles needed?** **No.** There is no supported flag, enterprise policy, or
Chrome profile configuration that makes desktop push deliver with the browser fully quit. The
background-process toggle (*"Continue running background apps when Google Chrome is closed"*) applies
to **Chrome extensions**, not to web push for a website. (Chromium extensions group:
<https://groups.google.com/a/chromium.org/g/chromium-extensions/c/yN1l8XAWhOc> — "You cannot switch
on the toggle programmatically… it is enabled by default.")

**Design consequence — this is why your graceful degradation matters:**

| State | Behaviour |
|---|---|
| Browser process running, no tabs open (tray/minimised) | ✅ Push delivered, OS notification shown. **This is the normal, good case.** |
| Tab open (any page) | ✅ Delivered. Post to the page → in-page toast. |
| Browser fully quit | ❌ Not delivered until the browser restarts (within `TTL`). |
| OS asleep / hibernated | ❌ Suspended. Delivered on wake (within `TTL`) — devices re-establish the FCM/APNs connection then. |
| Device offline | ❌ Buffered by the push service for up to `TTL`. |

So: **ship the toast path as a first-class feature, not an error state.** The most common real-world
case for a personal planner is "browser was closed" — and no amount of push engineering fixes that
on desktop. State this in the UI: *"Keep the browser running (tray is fine) for OS notifications."*

  <https://developer.apple.com/forums/thread/732594>

  <https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers>

iOS 16.4 required the site to be opened from the Home Screen before the prompt appears.

**Practical iOS handling:**
1. Detect and explain: if iOS and not standalone, push the user through Share → Add to Home Screen
   → open from Home Screen → then hit Subscribe.
2. Detect standalone: `window.navigator.standalone === true` (iOS) or
   `matchMedia('(display-mode: standalone)').matches`.
3. Ship a web app manifest with `display: "standalone"` — mandatory for iOS web push.
4. **Never skip `showNotification()` on iOS.** Permission gets revoked silently otherwise.

### 5.3 VAPID key rotation

**Yes — existing subscriptions break.** From RFC 8292 §4.2 (*"Subscription Restriction"*):

> "When a push message subscription has been restricted to an application server, the request for
> push message delivery MUST include a JWT signed by the private key that corresponds to the public
> key used when creating the subscription.
> A push service **MUST reject** a message sent to a restricted push message subscription if that
> message includes no 'vapid' authentication or invalid 'vapid' authentication. A **401
> (Unauthorized)** status code might be used if the authentication is absent; a **403 (Forbidden)**
> status code might be used if authentication is invalid."

The invalid-token cases include *"the public key used to sign the JWT doesn't match the one that
was included in the creation of the push message subscription"*.

RFC 8292 §5 spells out the recovery:
> "An application server that needs to replace its signing key needs to **request the creation of a
> new subscription by the user agent** that is restricted to the updated key. **Application servers
> need to remember the key that was used when requesting the creation of a subscription.**"

And the Push API spec (W3C):
> "Once set, **options for a push subscription cannot change.** A pre-existing push subscription can
> be unsubscribed, via `unsubscribe()`, to create a push subscription with new options."
> <https://www.w3.org/TR/2019/WD-push-api-20190711>

**What you'll actually observe:** after rotating `WEB_PUSH_PRIVATE_KEY`, sends to old endpoints
return **403** (not 404/410). Your §3.3 pruning logic **correctly does NOT prune on 403** — good,
because 403 is recoverable, not a dead endpoint.

**Rotation procedure:**
1. Deploy the new keypair alongside the old one (keep `WEB_PUSH_PRIVATE_KEY_PREVIOUS`).
2. Store a `vapid_key_id` column on `push_subscriptions` so you know which key each endpoint needs.
3. For each subscription, send using the key it was created with (transition period). RFC 9749 §5
   blesses exactly this: *"the server MAY continue to send push notifications for existing push
   subscriptions using the old application server key for a transitional period."*
4. The client must resubscribe — `unsubscribe()` then `subscribe()` with the new
   `applicationServerKey`. Because `options` cannot change on an existing subscription, this is
   **not** optional; there's no in-place update.
5. Add a `pushsubscriptionchange` handler — but see the warning below.
6. After the transition window, delete all `vapid_key_id = old` rows.

⚠️ **`pushsubscriptionchange` is not implemented in Chrome.** Long-standing Chromium bug
[646721](https://crbug.com/chromium/p/646721); developers confirm as of 2021–2024 that "chrome
doesn't support it." Safari doesn't either. So you cannot rely on the browser telling you to
resubscribe.

**Practical workaround for a single-user app:** store a `vapidKeyVersion` in your DB. In
`getCurrentPushSubscription()`, compare the browser's `subscription.options.applicationServerKey`
bytes against your *current* public key; if they differ, `unsubscribe()` + resubscribe
automatically on next page load. Roughly:

```ts
const expected = urlBase64ToUint8Array(process.env.NEXT_PUBLIC_VAPID_PUBLIC_KEY!);
const sub = await reg.pushManager.getSubscription();
if (sub) {
  const cur = sub.options.applicationServerKey;
  const rotated = !cur || Buffer.compare(
    Buffer.from(new Uint8Array(cur)),
    Buffer.from(expected)
  ) !== 0;
  if (rotated) {
    await sub.unsubscribe();
    // then subscribe() again with the new key, and POST to /api/push/subscribe
  }
}
```

**Simplest advice for a single-user planner: never rotate unless you must, and if you must, delete
your own subscription in DevTools (`Application → Service Workers → Unregister`, or
`pushManager.getSubscription().then(s => s.unsubscribe())`) and re-subscribe.** You'll fix it in
10 seconds; don't build migration machinery for one user.

### 5.4 Subscription expiry / "Chrome expires after ~30 days unused"

**⚠️ Your premise is only partly correct, and I could NOT verify the Chrome-specific claim.**

What I could verify:

- `PushSubscription.expirationTime` returns *"a `DOMHighResTimeStamp` of the subscription expiration
  time… **if there is one, or `null` otherwise**."*
  <https://developer.mozilla.org/en-US/docs/Web/API/PushSubscription/expirationTime>
  In Chrome this is **essentially always `null`** in practice. ⚠️ **UNVERIFIED** on current
  builds — I found no recent data.
- **Microsoft Edge** *does* set it, to **30 days from creation**, and implements
  `onpushsubscriptionchange` to let sites handle refreshes 5 days before expiry. Source: a 2018
  comment by a Chromium engineer on the Push API spec issue:
  *"Microsoft Edge sets expirationTime on the subscription (**30 days from creation**) and
  implements the onpushsubscriptionchange event that allows sites and apps to handle the case when
  Microsoft Edge refreshes a subscription that is 5 days from expiration. I anticipate that other
  browsers would be interested in setting expirationTime and implementing onpushsubscriptionchange
  as well… **Yeah, Chrome plans to match Edge in this regard.**"*
  <https://github.com/w3c/push-api/issues/302> — **⚠️ from 2018; I found no confirmation that
  Chrome actually shipped this.**
- The *goal* is documented in that same thread: *"The browser push service should detect inactive
  devices and mark the endpoint as expired (i.e. **return 410 Gone** to the application server)."*
- Independently: pushpad's research, *"Web push subscription age affects delivery rates"* —
  *"there is a **negative correlation between the age of a push subscription and its expected
  delivery rate**."* Cited in <https://github.com/w3c/push-api/issues/302>.
- Spec requirement (W3C): *"When the push subscription can no longer be used, for example because
  it has expired, the user agent MUST fire the `pushsubscriptionchange` event… with `oldSubscription`
  and `null` as `newSubscription`."* But Chrome doesn't implement the event, so this is academic.

**Bottom line: there is no fixed "Chrome expires after 30 days" rule you can rely on.** What is
certain and actionable:

1. **Endpoints do die.** 404/410 will happen — user clears site data, uninstalls the PWA, resets
   their profile, revokes notification permission, or the push service garbage-collects. Your §3.3
   pruning handles it.
2. **Delivery rate decays with subscription age** (the pushpad study). For a 5-minutely reminder
   that's fine, but it argues for the "re-subscribe when the key version differs" logic in §5.3,
   and for a periodic client-side `getSubscription()` health check.
3. **Don't write logic that keys off `expirationTime`.** It's `null` on the platform you'll use.

**Recommended cheap liveness check** — run it on app load, not on a timer:

```ts
export async function reconcileSubscription() {
  const sub = await getCurrentPushSubscription();
  if (!sub) return { status: 'no-subscription' as const };
  // sub.options.applicationServerKey -> compare to current key (§5.3)
  // sub.expirationTime -> if non-null and in the past, treat as dead
  if (sub.expirationTime !== null && sub.expirationTime < Date.now()) {
    await sub.unsubscribe();
    return { status: 'expired-client-reported' as const };
  }
  return { status: 'ok' as const };
}
```

## 6) Troubleshooting

### Nothing arrives at all

| Check | How |
|---|---|
| Are you on HTTPS? | `window.isSecureContext` must be `true`. `localhost` is exempt. |
| Is the SW registered at root scope? | DevTools → Application → Service Workers. Scope should read `/`. |
| Is the SW controlling the page? | `navigator.serviceWorker.controller` — `null` on the very first load; reload. |
| Is the script actually updated? | DevTools → Application → Service Workers → **Update on reload** / Unregister. `Cache-Control: no-cache` on `/sw.js` (§2.4). |
| Right JS media type? | `curl -I https://your-app.vercel.app/sw.js` → `Content-Type: application/javascript`. A wrong type fails registration silently. |
| Did `subscribe()` actually run? | `await navigator.serviceWorker.ready.then(r => r.pushManager.getSubscription())` in the console. |
| Did the server record it? | `select * from push_subscriptions;` |
| Is `WEB_PUSH_SUBJECT` valid? | Must be `https:` or `mailto:`. `mailto:x@localhost` → **Apple `403 BadJwtToken`**. |
| Did key validation pass at boot? | `setVapidDetails` throws if the public key isn't 65 bytes or the private key isn't 32 bytes (or if either contains `=`). Check `console.log(Buffer.from(PRIVATE,'base64url').length)`. |
| DevTools → Application → Notifications panel | Press `Ctrl+E` (⌘E on Mac) to start recording. You should see the `push` event fire even if the OS notification doesn't render. |

### Server returns 4xx

| Status | Cause | Fix |
|---|---|---|
| **400** | `BadJwtToken` / `InvalidTTL` / bad `Crypto-Key` | Usually a malformed VAPID key. Re-verify `generateVAPIDKeys()`. |
| **401** | Missing `vapid` `Authorization` header | `setVapidDetails()` not called, or the endpoint is a legacy GCM endpoint. |
| **403** | Invalid VAPID signature / claims / **key mismatch** | Wrong private key, or keys rotated (§5.3), or Apple rejecting a localhost subject. |
| **404** | Endpoint gone | **Prune.** §3.3. |
| **410** | Subscription expired/unsubscribed | **Prune.** §3.3. |
| **413** | Payload > 4096 octets encrypted / > 3993 plaintext | Shorten the body. Assert with `Buffer.byteLength()` (§3.1). |
| **429** | Push service rate limit | Back off. `topic` coalescing helps. Don't prune. |

### Scheduler never fires

| Symptom | Cause | Fix |
|---|---|---|
| Deploy fails with *"Hobby accounts are limited to daily cron jobs"* | Hobby plan + sub-daily cron | **Use Option C.** Can't be configured around. |
| No rows in `cron.job_run_details` | `pg_cron` not enabled / job not scheduled | `create extension pg_cron;` then re-run `cron.schedule(...)`. `select * from cron.job;` |
| `net._http_response` empty | `pg_net` not enabled, or transaction never committed | `pg_net` only fires requests **after commit**. Also: the job must be `select net.http_post(...)`, not a bare `net.http_post(...)` outside a SELECT. |
| 401 from the endpoint | `vault` secret ≠ `CRON_SECRET` | Re-read the vault row, compare against the Vercel production env var. |
| 404 from the endpoint | Path wrong, or the deployment is a preview | Cron registers on production only. Check the `vercel.json` `path`. |
| `pg_net` sends nothing useful | It's POST+JSON only | Make the route export `POST` (and `GET`). §4 Option C. |
| Duplicate notifications | Vercel "may occasionally invoke the same scheduled run more than once" | `notification_log` PK + the 90s lookback window. §3.3. |
| Vercel route returns 3xx | *"Cron jobs do not follow redirects"* | Return `Response.json(...)`, never a redirect. |

### Notification shows but clicking does nothing

- Missing `event.waitUntil()` in the handler — the SW is torn down mid-`focus()`/`navigate()`.
- `client.navigate()` is Chrome/Edge only. Safari needs `client.postMessage()` + your app's own
  router. Handle the rejection (§2.6).
- `clients.matchAll()` with default options returns **zero** clients when the page is not yet
  controlled. Use `{ includeUncontrolled: true }`.
- Cross-origin client matched first → `focus()` throws. Filter by
  `new URL(client.url).origin !== self.location.origin`.
- `actions` silently missing on desktop → you passed `type: 'text'` (reply) or used the
  `Notification` constructor instead of `registration.showNotification()`. §2.7.

### Works on desktop, nothing on iPhone

- Not added to Home Screen, or permission prompt attempted outside a user gesture. §5.2.
- No web app manifest / `display` not `standalone`.
- SW handler took a path that didn't call `showNotification()` — Safari revokes permission. §2.3.
